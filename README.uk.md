# Бот лісових порад (RAG-бот Мишки-шкряботушки)

[English](README.md) · **Українська**

Telegram-бот для лісової громади. Звірі надсилають документи з порадами; будь-хто може поставити
питання звичайним текстом і отримати відповідь **лише з цих документів, завжди з джерелом**:

> **П:** Скільки внесок під дубом і до якого числа?
> **В:** 4 жолуді з дорослого звіра на місяць, здати до 10 числа.
> — з документа «Членські внески» рукавички «Під дубом»

Усі вимоги, зібрані від клієнтки й кожна підтверджена нею, — у
[REQUIREMENTS.md](REQUIREMENTS.md).

## Запуск

```bash
cp .env.example .env   # далі заповніть BOT_TOKEN і GROQ_API_KEY
docker compose up --build
```

От і все: стартує PostgreSQL, бот створює таблиці, імпортує «Лісовий архів» (під час першого
запуску розпізнає OCR ~20 сканованих PDF, це близько хвилини) і починає polling.

| Змінна | Обов'язкова | За замовчуванням | Значення |
|---|---|---|---|
| `BOT_TOKEN` | так | | Токен Telegram-бота від @BotFather |
| `GROQ_API_KEY` | так | | Ключ Groq API (безкоштовного тарифу достатньо) |
| `GROQ_MODEL` | ні | `openai/gpt-oss-120b` | Модель, що пише відповіді |
| `GROQ_ROUTER_MODEL` | ні | `openai/gpt-oss-20b` | Модель, що вибирає документи й класифікує завантаження |
| `GROQ_REASONING_EFFORT` | ні | `low` | `low` / `medium` / `high` |
| `TIMEZONE` | ні | `Europe/Kyiv` | Часовий пояс для «надіслав …, 12.10 о 14:30» |
| `POSTGRES_PASSWORD` | ні | `bot` | Пароль БД (БД не доступна ззовні Docker) |

Якщо обов'язкова змінна відсутня чи порожня, бот зупиняється на старті з зрозумілою помилкою.

## Як користуватися ботом

Команд немає: **будь-яке текстове повідомлення — це питання, будь-який файл — порада.**

- **Запитати**: назвіть місце, напр. «що їсти біля мурашника?». Уточнення працюють: «а до якого
  числа?» бере місце з попереднього питання.
- **Поділитися порадою**: надішліть файл PDF, Word (.docx) або .txt. Під час першого завантаження
  бот питає ваше ім'я. Місце він визначає з документа; якщо незрозуміло — **питає вас** (кнопками),
  ніколи не вгадує.

## Як це працює

```
питання ─► фільтр місць ─► router LLM (за назвами) ┐
           (код)           пошук BM25 (за текстом) ┴─► вибір 1 документа ─► відповідь з нього ─► 1 цитата
```

1. **Фільтр місць** (`bot/retrieval.py`, `bot/places.py`). Документ належить усьому лісу, одній
   зоні (хвойна / листяна / річкова) або одному місцю. Якщо питання називає місце, кандидатами є
   лише документи цього місця + його зон + усього лісу. «Під вербою» входить у дві зони; «На
   узліссі» — у жодну. Звичайний код: точно, легко тестувати.
2. **Гібридний пошук.** Мала модель (`gpt-oss-20b`) вибирає документи за *змістом* їхніх назв
   («поїсти» → «Чим поживитись»); BM25 знаходить *слова всередині* тексту («тиша» — це розділ
   «Правил співжиття»). У Groq немає моделі ембедингів, а список документів малий, тож векторна БД не потрібна.
3. **Спершу вибір, потім відповідь** (`gpt-oss-120b`). Одна відповідь — з **одного документа**:
   - *Вибір*: модель бачить кандидатів і повертає лише `{status, source, question}`: номер одного
     найрелевантнішого документа (документ для конкретного місця важливіший за загальний — правило
     клієнтки) і питання, переписане як самостійне з урахуванням попередніх *питань* (ніколи не
     попередніх відповідей). Відповіді вона не пише.
   - *Відповідь*: другий виклик бачить **лише цей документ** і питання, тож домішати нема чого.
     Прямі факти або те, що з них логічно випливає («6 жолудів більше за потрібні 5»), або
     `found: false`.
   - **Код** додає цю єдину цитату. «Не знайдено», «покажи всі поради», порівняння й питання, яким
     потрібне неназване місце, отримують фіксовані відповіді, написані кодом, без цитати.
4. **Завантаження** (`bot/parsing.py`, `bot/llm.py`). Текст парситься (pypdf, python-docx,
   Tesseract OCR для сканів). Router-модель повертає назву й область дії; `unclear` → бот питає
   відправника.
5. **Версії** (`bot/documents.py`). Та сама нормалізована назва + та сама область дії = нова
   версія: стара деактивується (зберігається для історії), а відповіді цитують нового відправника й
   час. Той самий файл, надісланий двічі, розпізнається за хешем.

### «Лісовий архів»

Папку клієнтки на Google Drive збережено знімком у `data/archive/` (78 файлів). `manifest.json`
містить назву й область дії кожного файлу. Щоб його заповнити, я прочитав кожен документ, бо назви
вводять в оману: «Коли падають жолуді й горіхи» — для листяного лісу, а «Як не заблукати серед
однакових сосен» — для всього хвойного лісу, а не для місця «У соснах». Імпорт ідемпотентний (за
хешем файлу): перезапуски не запускають OCR повторно, а документ архіву, замінений звіром, не
повертається.

### Рішення щодо дизайну

- **AsyncGroq, один клієнт** на весь застосунок: виклики Groq обмежені вводом-виводом (async
  тримає бота активним); один клієнт перевикористовує HTTPS-з'єднання. OCR навантажує процесор, тому
  він працює в `asyncio.to_thread`.
- **Ліміти безкоштовного тарифу** (8k токенів/хв на модель): дві моделі з окремими лімітами,
  короткий контекст (≤10 невеликих документів), `reasoning_effort=low`. Якщо Groq не відповідає,
  користувач отримує дружнє повідомлення.
- **Prompt injection**: завантажені документи — недовірені дані. Промпти кажуть моделі, що текст
  документа — це дані, а не інструкції, а цитати формує код, а не модель.
- **PostgreSQL + Docker volume**: документи й імена переживають перезапуски. Таблиці створюються
  через `create_all`; у реальному проєкті додав би міграції Alembic.
- **Пам'ять розмови** живе в процесі (останні 3 питання на чат): вона потрібна лише для уточнень.
- **Спершу заміна, скасування на «Ні»**: ймовірна нова версія під іншою назвою одразу замінює стару
  (правило клієнтки: новіша версія завжди замінює стару), а відправник отримує одну кнопку, щоб
  скасувати заміну. Скасування працює лише для останньої заміни відправника і лише поки нова версія
  ще остання; старіші кнопки скасування стають недійсними, а кнопка не містить жодних id.

## Обмеження й масштабування

Розраховано на цифри клієнтки: кілька сотень документів за сезон і десятки звірів одночасно.
Відомі обмеження і що я змінив би далі:

- **Ріст промпту router-а:** router бачить назву кожного документа-кандидата, тож його промпт росте
  з кожним новим завантаженням. На кількох сотнях документів це перше, що впреться в ліміт 8k
  токенів/хв безкоштовного тарифу. Рішення: нехай BM25 спершу відбирає 30–40 назв і router бачить
  лише їх, тоді промпт лишається того самого розміру, хоч яким великим стане архів.
- **Стан FSM і пам'ять чату** зберігаються в оперативній пам'яті бота. Якщо бот перезапуститься,
  поки чекає на відповідь звіра (ім'я, місце чи «Так/Ні»), незавершене завантаження втрачається, а
  уточнення втрачають контекст. Рішення: `RedisStorage` з aiogram і пам'ять на Redis, щоб і те, і
  те переживало перезапуски.
- **Тести працюють на SQLite**, продакшн — на Postgres. SQLite швидкий і не потребує сервера, але
  поблажливіший: за замовчуванням він не перевіряє зовнішні ключі, тож документ, що посилається на
  неіснуючого користувача, пройде тести й впаде в продакшні. Рішення: проганяти ті самі тести на
  Postgres через testcontainers, відкочуючи транзакцію кожного тесту для ізоляції.
- **Довгі документи:** кожен документ обрізається до перших 6000 символів, перш ніж його побачить
  модель, тож на пораду глибоко в довгому документі відповісти не вийде: звір почує «нічого не
  знаю» про те, що збережено, і жодної помилки не буде видно. Рішення: під час збереження ділити
  документи на фрагменти за розділами, шукати по фрагментах і давати моделі найкращий, але
  цитувати весь документ.
- **Пропущені версії:** нову версію під іншою назвою визначає LLM. Якщо вона пропустить збіг або
  перевірка впаде, обидві версії лишаються активними. Рішення: додатково порівнювати текст через
  BM25 і позначати дуже схожі поради в тому самому місці.

## Розробка

```bash
uv sync
uv run pytest            # тести на SQLite з замоканою LLM; мережа не потрібна
uv run python -m bot.main  # потрібен DATABASE_URL, напр. sqlite+aiosqlite:///bot.db, і Tesseract для сканів
```

```
bot/
  main.py        старт: БД, імпорт архіву, polling
  handlers.py    лише шар Telegram
  qa.py          питання → документи → відповідь + цитати
  retrieval.py   фільтр місць + BM25
  llm.py         виклики Groq (відповідь, router, класифікатор); промпти в prompts.py
  documents.py   зберігання, версії, цитати
  parsing.py     PDF / DOCX / TXT + OCR
  archive.py     імпорт «Лісового архіву»
  places.py      8 місць і 3 зони
  db.py, config.py, memory.py
data/archive/    знімок архіву + manifest.json
tests/
```
